## Admission, suppression et dispatch

Admission HTTP persistante HMAC namespace distinct de B2, pas IP/email brut, aucun bucket par token arbitraire ; contrôle avant KDF, TTL/purge/cap fermes et refus ne prolongeant pas fenêtre. Limites techniques configurables documentées (login5/min adresse,20/min pair comme point de départ ; plafonds globaux/csrf/proof bornés). REMOTE_ADDR seul, pas XFF/Forwarded client, pair proxy Render éventuellement partagé donc aucune prétention IP visiteur fiable. Concurrence auth2/process et wait borné, timeouts statement/lock privés ; garder découverte disponible. Transaction admission courte COMMIT et fermée AVANT Account métier, aucun cycle Admission↔Account/Budget. Refus comptabilisé indépendamment d'un rollback métier.

Suppression : réauth+CSRF, atomique own Account/credentials/sessions/challenges/SavedEntry CASCADE ; purge des buckets B2 pour l'adresse connue sous ordre Account→Budget→quota, compteurs globaux agrégés et autrui conservés. Admission HTTP anti-abus indépendante conservée seulement son TTL documenté, pas effacement anti-abus global ; ne pas promettre disparition de toute trace pseudonyme avant TTL. Re-register ne remet pas à zéro budget global ni admission. Fichiers source/catalogue/epoch inchangés. Aucune promesse effacement immédiat chez fournisseur (pas encore de données réelles).

Dispatch Queue RAM max16 +1 worker/process : insertion non bloquante APRÈS vrai commit ET fermeture Session ; transporter intent privé, pas ORM/requestcontext. Pas réseau dans commit callbacks/after_request/transaction ; 202 sans attendre worker pour connu/inconnu/limité/panne/full. File pleine/perte crash : résultat générique, réservation conservée, renvoi récupération ; pas durable outbox/token DB/fichier, pas retry/service externe/cron. Lifecycle start une fois app activée, arrêt/drain bornés tests/process, jamais teardown_request ; pas worker si disabled/config fermée. Blocage provider ne bloque pas réponse, démontré par barrières plutôt que seuil fragile. Arrêt doit retirer/abandonner les messages encore en attente et signaler honnêtement si le thread actif n'est pas fini : pas de hard-cancel garanti d'I/O Python, tests libèrent ensuite leur barrière et drainent. Après suppression réussie, retirer les messages de ce compte encore en attente dans la file bornée ; un item déjà pris par le worker ou accepté chez provider peut encore partir, mais CASCADE rend sa preuve invalide. Test spécifique suppression/queue/in-flight, sans appel provider sous verrou DB ou prétention effacement distant. Mesurer variations KDF/DB connues/inconnues/confirmées/limitées, équilibrer coût registration si nécessaire ; ne jamais affirmer temps constant global ni capacité Render sur mock.
